## 1. Executive Summary

### 1.1 프로젝트 정의
성남 KDT 교육과정 운영에서 반복되는 **행정·출결·자료·질문 소통의 마찰을 하나의 웹 플랫폼(LMS)으로 통합**하고, 수료 시점의 **취업 서류 준비와 면접 대비를 AI로 지원**하며, 팀 프로젝트 결과물을 **외부에 보여주는 쇼케이스**까지 연결하는 서비스입니다.

### 1.2 비전
> "학원 담당자와 강사는 단순 행정에서 벗어나고, 교육생은 수강 초중반부터 포트폴리오를 쌓아 수료 시점에 서류와 면접 준비를 갖춘다."

### 1.3 기능 카테고리 개요

| # | 카테고리 | 대표 기능 |
| :--- | :--- | :--- |
| A | 학사 행정 & 운영 DX | 자료·과제 아카이브, 결석계 티켓, **출결 방어 대시보드**, **규정 챗봇** |
| B | 학습 협업 & 피어 러닝 | **팀 프로젝트 빌딩·가이드**, 기술 Q&A 게시판 |
| C | 취업 지원 & 커리어 AX | 이력서·자소서 수합, **면접 질문 생성기**, (확장) 이력서 첨삭 엔진 |
| D | 반별 공간 & 역할별 대시보드 | 반 단위 데이터 분리, 학원 관계자·강사·수강생 대시보드 |
| E | 마켓플레이스(쇼케이스) | 프로젝트 공개 페이지, 기업 문의(커피챗/PoC) 폼 — 로그인 없이 외부 공개 |

### 1.4 우선순위 원칙
1. **행정 마찰 제거가 먼저**: 자료, 티켓, 서류 수합, 출결이 돌아가야 사용자가 생긴다.
2. **이미 개발이 확정된 AI 기능은 통합이 목표**: 규정 챗봇과 면접 질문 생성기는 독립 개발되고, LMS는 API로 연결한다.
3. **외부 노출 기능은 마지막**: 쇼케이스·B2B는 내부 운영이 안정된 뒤 진행한다.
4. **실사용 우선**: 기능 수보다 "실제로 쓰는 사람이 있는 것"을 목표로 한다.
5. **빠르고 가볍게**: 강사·수강생·학원 관계자 모두 대시보드 한 화면에서 필요한 정보를 확인하고, 페이지 이동을 최소화한다.

### 1.5 프로젝트 목표 (팀 공통)
- 실제 사용자(교육생·강사·학원 담당자)가 있는 **실서비스를 올해 안에 배포**한다.
- 모든 팀원이 기획·설계·구현·운영 중 **자신이 맡은 영역의 결정과 기록을 포트폴리오로 남긴다**.

## 2. 배경 및 문제 정의 (AS-IS vs TO-BE)

### 2.1 AS-IS: 병목 분석

| 영역 | 현재 상태 | 발생 비용 |
| :--- | :--- | :--- |
| 자료 공유 | 슬랙 채널에 강사별 재량으로 자료·실습 코드 배포 | 자료 위치 혼선, 이전 주차 탐색 비용 |
| 결석 처리 | 결석/공결 사유서, 처방전 사진을 카톡으로 수합 | 누락, 증빙 분실, 감사 대비 부담 |
| 출결 관리 | 단위기간별 출석률 80% 요건을 수기 계산 | 사전 경고 부재, 미달 후에야 인지 |
| 반복 문의 | 출석 인정 기준, 장려금 지급일 등을 담당자가 개별 응답 | 담당자 소모, 답변 불일치 |
| 서류 수합 | 이력서·자소서가 카톡/개별 전달 | 버전 혼재, 제출·첨삭 현황 파악 불가 |
| 팀 프로젝트 | 팀 구성·기획안·진행 점검이 개별 채널에 분산 | 강사 가이드 시점 지연, 중도 이탈 파악 어려움 |
| 피어 러닝 | 에러 로그·환경 이슈를 묻고 답할 전용 채널 부재 | 환경 정보 누락으로 디버깅 왕복 증가 |
| 면접 대비 | 혼자 준비하거나 즉흥적인 모의면접 | 이력서의 약한 지점을 짚는 질문 경험 부족 |
| 성과 노출 | 최종 프로젝트가 수료와 함께 사장됨 | 채용·외부 협업 기회로 이어지지 않음 |

### 2.2 TO-BE

| 영역 | 목표 상태 |
| :--- | :--- |
| 자료 | 주차별 커리큘럼 트리 단일화, 과제 제출함 포함 |
| 결석 | 수강생이 모바일로 사유·증빙 접수, 담당자는 팝업으로 즉시 확인 |
| 출결 | 수강생 명부에서 결석·지각·조퇴를 기록하면 단위기간별 잔여 허용 결석일수와 경고 등급 자동 산출 (엑셀 반복 업로드 없음) |
| 반 운영 | 반별로 공간·데이터 분리, 반마다 담당 매니저 배정, 역할별 대시보드로 한 화면 확인 |
| 문의 | 매뉴얼 기반 챗봇이 24시간 응대, 근거 문서 표시 |
| 서류 | 템플릿 제공, 상태(초안 → 첨삭 중 → 완성) 일괄 트래킹 |
| 팀 프로젝트 | 팀 빌딩, 기획안, 마일스톤, 강사 피드백을 한 화면에서 관리 |
| 면접 | 이력서 PDF의 결손점을 짚는 질문과 평가 체크포인트 자동 생성 |
| 성과 | 팀별 원페이지 쇼케이스와 기업 문의 폼으로 외부 연결 |

### 2.3 신입 개발자 대상 전제
- 이력서·면접 지원 대상은 **신입 개발자 직군 전반**(백엔드·프론트·AI 등)이다.
- 신입에게 기대되는 것은 "대단한 성과"가 아니라 **무엇을 왜 만들었는지, 내 역할은 무엇이었는지, 어떻게 확인했는지, 막혔을 때 어떻게 풀었는지**이다. 질문과 평가 기준도 여기에 맞춘다.
- 피지컬 AI 등 과정에서 배우는 특정 기술은 지원 직군의 한 예일 뿐 서비스의 전제가 아니다.

### 2.4 데이터 순환 구조

```
이력서 PDF 업로드
  ▶ 면접 질문 + 평가 체크포인트 생성 (AI)
  ▶ 강사 1:1 모의면접, 평가 폼 입력
  ▶ 피드백이 수강생 마이페이지에 아카이빙
  ▶ 이력서 보완 → 재업로드
  ▶ (동의한 건만) 품질 개선·평가셋 구축에 활용
```

> 학습·개선 목적의 데이터 활용은 **제출 시점의 명시적 동의**를 받은 건에 한정한다. (8.1 참고)

### [M0] 반(Cohort) 구조·계정·접근 범위 (P0, 기반)

**목적**: 모든 데이터를 **반 단위로 분리**하고, 누가 어떤 반을 볼 수 있는지를 한 곳에서 정의한다. 나머지 모듈의 전제이므로 W3에 가장 먼저 구현한다.

**구조 규칙**
- **학원(Academy) → 반(Cohort)** 구조이고, **반 = 하나의 과정 운영 단위**이다. 수강생은 **한 반에만** 소속된다. 현재는 한 학원이지만 학원 단위 분리를 데이터 모델에 처음부터 둔다.
- 과정의 길이와 성격이 반마다 다르므로(6개월, 2개월 등) **훈련 기간, 단위기간, 단계 가이드, 기능 사용 여부는 모두 반 설정값**으로 둔다.
- 반마다 **담당 매니저 1명**(주담당)이 기본이다. **대체 담당은 두지 않으며**, 담당자 부재 시에는 학원 슈퍼어드민이 처리한다.
- **한 명의 매니저가 여러 반을 담당**할 수 있다. 강사도 여러 반에 배정될 수 있다.
- **학원 슈퍼어드민**(`ACADEMY_ADMIN`)은 학원별로 지정되며, 소속 학원의 **모든 반에 접근**하고 반 개설·계정 발급·명부 관리를 수행한다. 다른 학원의 데이터는 접근할 수 없다.
- 반에 종속되는 모든 데이터(자료, 과제, 티켓, 출결, 서류, 팀, 프로젝트)는 `cohortId`를 가지며, **서버가 접근 가능한 반으로 항상 제한**한다.

**계정 발급 (회원가입 없음)**
- 자체 회원가입은 없다. 학원 슈퍼어드민이 반 개설 후 명부(CSV: 이름, 로그인 ID, 연락처(선택), 역할)를 업로드해 **강사·수강생 계정을 일괄 생성**한다. 슈퍼어드민 계정은 개발팀이 학원별로 발급한다. `[TBD: 매니저 계정 발급 주체, 로그인 ID 형식]`
- 초기 비밀번호는 임시값을 자동 생성해 **발급 직후 1회만** 목록(CSV)으로 내려받게 하고, **최초 로그인 시 변경을 강제**한다. 비밀번호 재설정은 슈퍼어드민이 처리한다.
- 이후 변동(중도 이탈·합류)은 명부 화면에서 개별 수정한다. 이탈자는 계정을 비활성화한다. 업로드 원본 파일과 임시 비밀번호 목록은 반영 후 서버에서 폐기한다.

**티켓 라우팅**: 티켓은 해당 반의 주담당 매니저에게 자동 배정된다. 주담당이 부재하면 학원 슈퍼어드민이 처리한다.

| 모델 | 주요 필드 |
| :--- | :--- |
| `Academy` | `name`, `status` |
| `Cohort` | `academyId`, `name`(과정명), `trainingType`(훈련직종, 예: K-Digital Training), `room`(강의실, 예: 6층 609호), `startDate`, `endDate`, `weeklySchedule(JSON)`(요일별 훈련 시작·종료 시각), `holidays(JSON)`(휴강일), `status(ACTIVE/ENDED)`, `attendanceConfig(JSON)`, `featureFlags(JSON)` |
| `CohortStaff` | `cohortId`, `userId`, `staffRole(MANAGER/INSTRUCTOR)`, `title`(담임교사/수업교사 등 표시용 직함), `isPrimary` |
| `Enrollment` | `cohortId`, `studentId`, `status(ENROLLED/DROPPED/COMPLETED)`, `enrolledAt` |
| `User` | `academyId`, `role(STUDENT/INSTRUCTOR/MANAGER/ACADEMY_ADMIN/ADMIN)`, `loginId`, `name`, `email?`, `status`, `mustChangePassword` |

**AC**: 반 A 담당 매니저가 반 B의 데이터를 화면·API 어디서도 조회할 수 없다 (자동 테스트 필수). 학원 슈퍼어드민은 자기 학원의 모든 반을 볼 수 있고 다른 학원 데이터는 볼 수 없다. 여러 반 담당자는 반 전환 한 번으로 이동한다.

### [M1] 커리큘럼·과제 아카이브 (P0)

**주요 기능**
- 반(Cohort) → 주차(Week) → 세션(Session) 트리, 세션별 자료(문서, 파일, 코드 저장소, 환경 가이드)
- 과제 제출함: 강사가 과제를 만들고 수강생이 제출, 제출 상태 확인
- 검색(제목·태그), 북마크

| :--- | :--- |
| `Cohort`(반) | M0 참조 |
| `Week` / `Session` | `weekNo`, `title`, `date`, `instructorId` |
| `Material` | `sessionId`, `type(DOC/FILE/REPO/GUIDE)`, `title`, `url`, `tags[]` |
| `Assignment` | `sessionId`, `title`, `dueAt`, `description` |

### [M2] 행정 티켓·결석계 (P0)

**목적**: 카톡 1:1로 흩어진 요청을 상태 있는 티켓으로 바꾼다. 결석계는 M3 출결 기록과 연결된다.

**티켓 유형**: `ABSENCE`(결석/공결), `COUNSELING`(면담), `DOCUMENT`(서류), `OTHER`

**상태 머신**

```
정상 흐름:  PENDING → IN_REVIEW → APPROVED
반려:       IN_REVIEW → REJECTED
보완 요청:  IN_REVIEW → NEEDS_REVISION → (재제출) → PENDING
취소:       PENDING → CANCELED
```

| 전이 | 가능 주체 | 조건 |
| :--- | :--- | :--- |
| PENDING → IN_REVIEW | INSTRUCTOR, MANAGER | — |
| IN_REVIEW → APPROVED | INSTRUCTOR, MANAGER | 결석계 승인 시 출결 기록 연동 |
| IN_REVIEW → REJECTED | INSTRUCTOR, MANAGER | **반려 사유 필수** |
| IN_REVIEW → NEEDS_REVISION | INSTRUCTOR, MANAGER | 보완 요청 코멘트 필수 |
| NEEDS_REVISION → PENDING | STUDENT | 재제출 |
| PENDING → CANCELED | STUDENT | 본인 티켓, 검토 시작 전만 |

모든 전이는 `TicketEvent`(누가/언제/무엇을/사유)로 기록한다. 티켓은 해당 반의 주담당 매니저에게 자동 배정된다. (M0)

**결석계 모바일 접수**
- 수강생 마이페이지에서 결석 일자, 사유 유형(병결, 휴가, 기타), 증빙 사진(처방전, 진료확인서 등) 업로드. 병결·휴가는 승인 시 출석으로 처리되며 횟수 제한이 적용된다. (M3)
- 담당자는 출결 화면에서 해당 결석 기록을 클릭하면 **증빙 이미지를 팝업으로 확인**
- 증빙은 접근 권한을 엄격히 제한하고 보관 기간을 둔다. (8.1 참고)

| 모델 | 주요 필드 |
| :--- | :--- |
| `Ticket` | `type`, `status`, `requesterId`, `assigneeId?`, `title`, `body` |
| `TicketAttachment` | `ticketId`, `fileUrl`, `mimeType`, `size` |
| `TicketEvent` | `ticketId`, `actorId`, `from`, `to`, `comment?`, `createdAt` |
| `AbsenceDetail` | `ticketId`, `absentDate`, `reasonType`, `isOfficial`, `linkedAttendanceEventId?` |

**AC**: 신청자가 현재 상태와 처리 이력을 확인한다. 허용되지 않은 상태 전이는 서버에서 차단된다.

### [M3] 출결 관리·방어 — 명부 카운팅 (P1)

**목적**: 단위기간별 출석률 80% 미달을 사전에 방어한다. 학원이 결석·지각·조퇴를 별도로 관리하므로, LMS는 **엑셀을 반복 업로드하지 않고 수강생 명부 화면에서 직접 기록·집계**해 **잔여 허용 결석일수**를 계산한다.

**입력 방식 (매니저 — 출결 입력 주체는 학원 담당자이며, 강사는 열람만 한다)**
- **오늘 출결 모드**: 반 명부가 전원 "출석"으로 열리고, 예외(결석·지각·조퇴·외출)만 눌러 기록한다.
- **명부 카운터 뷰**: 수강생별 `결석 / 지각 / 조퇴 / 외출` 누계, 환산 결석, 잔여 허용 결석일, 등급을 한 표에 보여주고 `+` / `−`로 빠르게 가감한다. 가감 시 날짜를 함께 기록한다(기본 오늘).
- 결석계(M2)가 승인되면 해당 일자의 결석이 **공결로 자동 반영**되어 입력 부담을 줄인다.
- **일일 출결 확인**: 하루 입력을 마치면 `[오늘 출결 확인 완료]`를 누른다. 예외가 없는 날은 이 버튼 한 번으로 끝난다. 입력하지 않은 날이 "전원 출석"으로 계산되어 잔여 허용 결석일이 실제보다 넉넉하게 보이는 것을 막기 위해, 화면에는 **확인 완료된 마지막 날**(최종 반영일)을 표시하고 미확인 일이 있으면 경고한다.
- 모든 변경은 **변경 이력**(누가·언제·무엇을)으로 남긴다.

**훈련 일정 설정 (반 개설 시 1회)**: 훈련 시작·종료일과 휴강일을 입력하면 주말·공휴일을 제외한 훈련일이 생성되고, **단위기간은 기본 분할(훈련 시작일 기준 1개월)을 제안한 뒤 매니저가 반 설정에서 직접 지정·수정**한다. 훈련일수 `N`은 이 일정에서 계산한다. (엑셀 없이 `N`을 얻기 위해 필요)

**초기 이관 (시범 시작 시 1회)**: 이미 진행 중인 반은 과거 일자별 기록을 다시 입력하지 않는다. 현재 단위기간의 수강생별 누적 `결석 / 지각 / 조퇴 / 외출`과 기준일(`asOfDate`)을 명부 화면의 표에 한 번에 입력(붙여넣기 지원)하고, 이후는 일자별 이벤트로 쌓는다. 집계 = 이관값 + 기준일 이후 이벤트. `[TBD: 과정 전체 누적 출석률 요건도 표시할지]`

**계산 정의 (일부 확정, 나머지는 학원 규정 확인 후 — 값은 `Cohort.attendanceConfig`에 저장해 반별로 조정)**

| 항목 | 정의 |
| :--- | :--- |
| 단위기간 | 반 설정에서 지정한다 (학원이 정한 구간) |
| 훈련 시간 | 반의 `weeklySchedule`에서 요일별로 정한다 (예: 월~목 09:00-17:40, 금 09:00-16:40). 금요일처럼 요일마다 종료 시각이 다를 수 있다. 지각·조퇴를 시각으로 판정할지 담당자 판단으로 입력할지 `[TBD: 확인]` |
| 총 훈련일수 `N` | 단위기간 내 훈련일 (훈련 요일·기간에서 계산, 휴강일 제외) |
| 허용 결석일수 | `floor(N × 0.2)` (정수 연산으로 구현) |
| 환산 결석일수 | 결석(공결 제외) + `floor((지각 + 조퇴) ÷ 3)` — **지각·조퇴 3회 = 결석 1일** (`k`는 반 설정값, 기본 3). 지각·조퇴 합산 여부와 외출 처리 `[TBD: 확인]` |
| 공결 | **병결·휴가는 출석으로 처리**하되 **횟수 제한**이 있다. 제한 횟수, 적용 기준(단위기간별/과정 전체), 초과 시 처리는 반 설정(`excusedLimit`)으로 둔다 `[TBD: 학원 규정]` |
| 잔여 허용 결석일수 | 허용 결석일수 − 환산 결석일수 |
| 경고 등급 | 정상 / 주의 / 위험 `[TBD: 임계값, 예: 잔여 2일 이상 정상, 1일 주의, 0 이하 위험]` |

**표시 화면**
- 수강생: 홈 대시보드 위젯 (내 잔여 허용 결석일, 등급, 이번 단위기간 결석·지각·조퇴 수, 병결·휴가 사용 횟수(제한 대비), **최종 반영일**)
- 매니저: 반별 요약 카드(위험·주의 인원) + 명부 카운터 뷰, 행을 누르면 서랍(drawer)에 일자별 기록과 증빙 팝업
- 강사: 담당 반의 위험·주의 학생 목록 (열람 전용)

| 모델 | 주요 필드 |
| :--- | :--- |
| `TrainingDay` | `cohortId`, `date`, `isTraining`, `note?` |
| `AttendancePeriod` | `cohortId`, `label`, `startDate`, `endDate` (훈련일수는 `TrainingDay`에서 계산) |
| `AttendanceEvent` | `cohortId`, `studentId`, `date`, `type(ABSENT/LATE/EARLY_LEAVE/OUT)`, `excused`, `excusedType?(SICK/LEAVE)`, `ticketId?`, `note?`, `recordedBy`, `createdAt` |
| `AttendanceOpening` | `cohortId`, `periodId`, `studentId`, `absent`, `late`, `earlyLeave`, `out`, `excusedUsed`(병결·휴가 사용 횟수), `asOfDate`, `recordedBy` |
| `AttendanceDayClose` | `cohortId`, `date`, `closedBy`, `closedAt` (최종 반영일 = 확인 완료된 마지막 날) |
| `AttendanceEventLog` | `eventId`, `action(CREATE/UPDATE/DELETE)`, `actorId`, `before(JSON)`, `after(JSON)`, `createdAt` |

**설계 원칙**
- **누계는 저장하지 않고 일자별 이벤트에서 집계**한다(시범 시작 시의 초기 이관값만 예외). 숫자가 서로 어긋나지 않고, 정정과 감사 대응이 가능하다. 화면은 카운터처럼 보여도 내부는 이벤트다.
- LMS 출결은 학원의 공식 기록을 대체하지 않는 **관리·사전 경고용**이다. 공식 기록은 학원이 별도로 관리하는 것을 기준으로 하며, 화면에 "참고용"과 "최종 반영일"을 표시한다.
- 계산 로직은 **순수 함수로 분리하고 단위 테스트**를 작성한다. 학원 수기 계산과 샘플을 대조해 검증한다.

**AC**
- 매니저가 20명 반의 당일 출결 예외를 1분 이내에 입력할 수 있다. (이동 없이 한 화면)
- 학원 수기 계산과 대조한 검증 샘플이 100% 일치한다.
- 결석계 승인 시 해당 일자 결석이 공결로 자동 반영된다.
- 이미 진행 중인 반도 현재 누적 값을 1회 입력하면 첫날부터 잔여 허용 결석일이 표시된다.
- 확인 완료되지 않은 날이 있으면 수강생·매니저 화면에 최종 반영일과 경고가 표시된다.

**의존성**: 반별 훈련 일정(시작·종료, 휴강일), 출결·공결·지각조퇴 규정, 수강생 명부(M0), 현재 단위기간까지의 누적 출결 현황(초기 이관). `[TBD]`

### [M4] 규정·매뉴얼 챗봇 (P1, 개발 확정)

**개발 방침**
- **담당**: 이진호. **일정**: 2026-10-24(W3)까지 단독 개발.
- 구현 방식은 지금까지 학습한 범위에서 담당자가 결정한다. 단, **LMS와는 아래 HTTP API로만 연동**하여 구현 방식이 바뀌어도 LMS는 수정하지 않는다. (ADR로 선택 근거 기록)

**기능 요건**

### [M5] 팀 프로젝트 빌딩·가이드 (P1)

### [M8] 면접 질문 생성기 (P1, 개발 확정)

**목적**: 이력서 PDF를 파싱해 프로젝트 기재 내용, 사용 기술, 성능 수치의 **결손점을 짚는 꼬리 질문**과 면접관용 **평가 체크포인트**를 자동 생성한다.

**개발 방침**
- **담당**: 정명주, 최주원. **일정**: 10월 말 착수, 약 3주 (2026-10-27 ~ 11-14, W4~W6). KDT 메인 프로젝트로 개발한다.
- LMS와는 아래 API 규격으로 연동한다. 개발 기간 중 LMS는 **목(mock) 응답**으로 화면과 흐름을 먼저 구현하고, W7에 실제 서비스로 교체한다.
- v1은 상용 LLM API 기반으로 구현한다. 온프레미스·경량 모델 검증은 이후 확장으로 둔다. `[TBD]`

**처리 파이프라인**

```
PDF 입력
  ▶ 텍스트 추출 (스캔본 PDF 대응 여부 TBD)
  ▶ 섹션 구조화 (프로젝트 / 기술 스택 / 경력·활동 / 학력)
  ▶ 결손점 탐지 (아래 표)
  ▶ 질문 생성 (JSON 스키마 강제)
  ▶ 후처리 검증 (근거 문장 실재 확인, 중복 제거, 개수 조정)
  ▶ 질문 + 체크포인트 반환
```

**결손점 유형**

| 코드 | 유형 | 질문 방향 예시 |
| :--- | :--- | :--- |
| `ROLE_UNCLEAR` | 팀 프로젝트에서 본인 기여 불분명 | 직접 구현한 부분과 팀원이 한 부분을 구분해 설명해 보세요 |
| `METRIC_MISSING` | "개선했다"만 있고 수치·측정 방법 없음 | 어떻게 측정했고 전후 값은 얼마였나요 |
| `TECH_REASON_MISSING` | 기술 스택 나열만 있고 선택 이유 없음 | 이 기술을 선택한 이유와 대안은 무엇이었나요 |
| `TROUBLESHOOT_GAP` | 문제는 있으나 원인·해결 과정이 빠짐 | 원인을 어떻게 찾았고 다른 시도는 무엇이었나요 |
| `SCOPE_VAGUE` | 규모·기간·사용자 등 범위가 모호함 | 실제 사용자나 데이터 규모는 어느 정도였나요 |

**API 규격 (LMS ↔ 면접 질문 서비스)**

| Method | Path | 설명 |
| :--- | :--- | :--- |
| POST | `/v1/interview/questions` | 질문·체크포인트 생성 |
| GET | `/v1/health` | 상태 및 엔진 버전 |

```json
// 요청
{
  "requestId": "uuid",
  "resume": { "fileUrl": "<서명된 임시 URL>" },
  "targetRole": "백엔드 개발자",
  "questionCount": 10,
  "level": "junior"
}

// 응답
{
  "requestId": "uuid",
  "engineVersion": "api-v1.0",
  "questions": [
    {
      "id": "q1",
      "category": "METRIC_MISSING",
      "question": "목록 조회 속도를 개선했다고 하셨는데, 어떻게 측정했고 전후 값은 얼마였나요?",
      "basis": { "section": "projects[0]", "quote": "목록 속도 개선" },
      "checkpoints": ["측정 방법(도구·환경)을 설명한다", "개선 전후 수치를 제시한다", "원인과 개선 방법을 연결해 설명한다"],
      "followUps": ["데이터가 10배 늘면 어떻게 되나요?"]
    }
  ],
  "meta": { "latencyMs": 8200, "inputTokens": 2100, "outputTokens": 1300 }
}
```

**품질 규칙**
- **근거 기반**: 모든 질문은 이력서에 실재하는 `basis.quote`를 가져야 하며, 코드가 이를 검증한다. 근거를 확인할 수 없는 질문은 폐기한다.
- **사실 단정 금지**: 이력서에 없는 사실을 있는 것처럼 전제하는 질문을 만들지 않는다.
- **신입 눈높이**: 대규모 트래픽·운영 경험 등 신입에게 기대하기 어려운 내용을 전제하지 않는다.
- 타임아웃 60초, 실패 시 LMS는 재시도 안내를 표시한다. 이력서 원문은 로그에 남기지 않는다.

**평가 폼 (모의면접, P1 후반)**
- 질문별 체크포인트를 화면에 띄워 강사가 점수·코멘트를 입력
- 결과는 수강생 마이페이지에 아카이빙

| 모델 | 주요 필드 |
| :--- | :--- |
| `InterviewSession` | `studentId`, `documentVersionId`, `engineVersion`, `generatedAt`, `status` |
| `InterviewQuestion` | `sessionId`, `category`, `question`, `basisQuote`, `checkpoints(JSON)`, `followUps(JSON)` |
| `InterviewEvaluation` | `questionId`, `evaluatorId`, `score(1~5)`, `comment`, `createdAt` |
| `QuestionFeedback` | `questionId`, `userId`, `useful(boolean)` |

**테스트 데이터**: 동의를 받은 이력서 또는 합성 이력서로 평가셋(20건 이상 목표)을 만든다. 개인정보는 제거한다.

### [M9] 이력서 첨삭 엔진 (P2, 확장)

M7·M8 이후 확장 후보이다. 이력서 항목별로 루브릭 점수와 STAR 변환 제안을 제공한다. 이종섭이 R&D로 진행하며, 올해 배포 범위에는 포함하지 않는다.

| # | 루브릭 항목 | 배점 | 관점 |
| :--- | :--- | :--- | :--- |
| R1 | 문제 정의와 기여 명확성 | 25 | 무엇을 왜 만들었고 본인 역할이 구분되는가 |
| R2 | 기술 선택의 구체성 | 20 | 스택·버전·선택 이유가 있는가 |

### [M11] 역할별 대시보드·화면 구조 (P0)

**설계 원칙**
- 로그인하면 **내 역할의 홈 대시보드**로 바로 이동한다. 메뉴는 역할당 3~5개 이내로 제한한다.
- **대시보드 우선**: 자주 보는 정보는 홈에서 모두 확인하고, 상세 확인·입력은 **페이지 이동 없이 서랍(drawer)·모달**로 처리한다. 자주 하는 작업은 2클릭 이내.

- **반 컨텍스트**: 수강생은 본인 반에 고정되고 반 전환기가 없다. 강사·매니저는 담당 반 목록에서 고르고, 여러 반을 맡은 매니저와 학원 슈퍼어드민은 `전체 요약` 뷰를 추가로 가진다.

## 4. AI 컴포넌트 엔지니어링 명세

### 4.1 공통 원칙
- **서비스 분리**: 챗봇(M4)과 면접 질문 생성기(M8)는 독립 서비스·모듈로 개발하고, LMS는 어댑터 계층(`src/lib/ai/*`)에서 HTTP로만 호출한다.
- **목(mock) 우선**: 이종섭이 두 API 규격의 목 서버(고정 JSON 응답)를 제공한다. LMS 화면은 목 응답으로 먼저 개발한다.
- **환경 전환**: `CHATBOT_BASE_URL`, `INTERVIEW_BASE_URL`, `*_SERVICE_TOKEN` 환경변수로 목과 실서비스를 전환한다.
- **서버 사이드 호출만**: 브라우저에서 AI 서비스를 직접 호출하지 않는다.
- **날조 금지**: 입력에 없는 사실·수치를 만들지 않는다. 근거를 찾지 못하면 "모른다"고 응답한다.
- **비용·한도**: 요청당 토큰 상한, 사용자별 일일 호출 한도, 동일 입력 결과 캐시.
- **로그**: 요청 ID로 추적하되 이력서 원문·개인 식별 정보는 로그에 남기지 않는다.

## 5. 시스템 아키텍처 및 데이터 흐름

### 5.1 전체 구성

```
Client: Next.js (App Router) — public / student / instructor / manager / admin
   │  Server Actions / Route Handlers
   ▼
Next.js Server (Auth / RBAC, Prisma ORM, AI 어댑터)
   ├──▶ MariaDB / MySQL
   ├──▶ 파일 저장소 (첨부, 증빙, PDF)
   ├──▶ 챗봇 서비스 (M4)         ◀ 이진호 개발
   └──▶ 면접 질문 서비스 (M8)    ◀ 정명주·최주원 개발
              └──▶ LLM API

- 스택은 Next.js 15+ (App Router), TypeScript, Prisma, MariaDB/MySQL, Tailwind + shadcn/ui.
- LMS 본체는 이종섭이 구현하고, 개발 환경·API 규격·목 서버는 이종섭이 제공한다. 배포 환경은 5.6을 따른다.

권한 검증은 **서버 액션 내부에서 반드시 수행**하고, 화면 숨김은 UX 보조로만 쓴다.

| 항목 | 규칙 |

### 5.4 반 개설과 출결 처리 흐름

```
반 개설 (학원 슈퍼어드민)
  ▶ 훈련 일정·휴강일 입력 → 훈련일 생성 → 단위기간 지정
  ▶ 명부 CSV 업로드 → 강사·수강생 계정 일괄 발급 → 반 담당 매니저·강사 배정
  ▶ (진행 중인 반) 현재 단위기간 누적 출결 1회 이관

일일 운영
  ▶ 매니저가 명부에서 예외(결석·지각·조퇴·외출)를 기록
  ▶ AttendanceEvent 저장 (+ 변경 이력)
  ▶ [오늘 출결 확인 완료] → 최종 반영일 갱신
  ▶ 승인된 결석계(공결) 자동 반영
  ▶ 환산 결석 · 잔여 허용 결석일수 · 등급 계산 (조회 시 집계)
  ▶ 수강생 홈 위젯 / 매니저·강사 위험군 목록에 반영
```

### 5.5 진입 흐름과 화면 라우팅

```
/                        랜딩: [로그인 (LMS)] | [마켓플레이스]
/login                   로그인 (이미 로그인 상태면 역할 홈으로 바로 이동)
/market, /market/{slug}  마켓플레이스 (공개, 로그인 불필요)
/app                     로그인 후 역할별 홈 대시보드로 이동
/app/c/{cohortId}/...    반 단위 화면 (수강생: 본인 반 / 강사·매니저: 배정된 반)
/app/overview            여러 반 담당 매니저용 담당 반 요약
/admin                   시스템 관리 (개발팀 전용)
```

- 반은 **URL의 `cohortId` 값**으로 구분하고 서버가 요청마다 접근 권한을 확인한다. 반 전환이 URL 이동이라 링크 공유와 새로고침에도 안전하다.
- 역할별 레이아웃(`StudentLayout`, `InstructorLayout`, `ManagerLayout`)을 나누고 위젯 컴포넌트는 공유한다.
- 마켓플레이스는 LMS 인증과 분리된 공개 라우트이며 **공개 승인된 항목만** 노출한다. 구현 전에는 랜딩의 마켓플레이스 진입을 "준비 중"으로 둘 수 있다.
- LMS와 마켓플레이스는 **같은 도메인**에서 경로(`/app`, `/market`)로 구분한다. 기준 URL은 환경변수로만 참조해 도메인이 바뀌어도 코드 수정이 없게 한다. (5.6)
- 마켓플레이스 검색 노출(SEO)을 위해 정적 생성/ISR을 검토한다. `[TBD]`

| 환경 분리 | 개발(스테이징)과 운영 데이터를 분리한다. 협의 전 개발·시연에는 가상 데이터만 쓴다 |
| 백업 | DB 일일 덤프와 업로드 파일을 서버 외부 저장소에 보관하고, 복구 리허설을 1회 수행한다 |

| 모니터링 | 프로세스 재시작 정책, 디스크·메모리 알림, 접속 로그 |

```
<type>(<scope>): <요약>

**PR 규칙**
- 1 PR = 1 목적, 가급적 400줄 이내
